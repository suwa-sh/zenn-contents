# ダイジェスト: Deep Reviewは設計文書の未記載前提をどう返すか

- 元記事: [google-deep-review-research-p8_20261017.md](../../../../../articles/google-deep-review-research-p8_20261017.md) (Zenn 下書き、2026-10-17 時点)
- 記事の型: 混合 (仕組みの説明 + 使い方の判断 + 保存条件の確認)

## ひとことで言うと

Google の Deep Review は、文書を節に分けて並行点検し、節間の整合と外部の根拠を確かめて報告を返す。設計レビューでは報告を「未記載の前提・本文と図表の不一致・改善提案」の3種に分け、採否と書き戻し先は人が決める。

## メンタルモデル

### 処理の流れ: 最後の統合段で節をまたいで確かめる

![Deep Review の4段の処理](images/behavior.png)

報告を受け取ったあとの採否は、この4段の外にあり、人が担う。統合段では、必要に応じて論理チェックをやり直すこともある (図では省略)。

### 報告の扱い方: 3種に分け、別々の欄へ戻す

![報告を3種に分けて書き戻す](images/structure.png)

- 改善提案を「既に決めていた前提」として仕様に書かない。混ぜると、未決の空白と既決の挙動が区別できなくなる。
- 「提案の欄」は説明のために付けた名前。記事は「既決の挙動とは別の欄に置く」とだけ書いている。

## 具体例 (架空)

ある設計文書を通したら、次の3件が返ってきたとする。

| 返ってきた指摘 | 種類 | 置く欄 |
|---|---|---|
| キャッシュの無効化が、本文に書いていない「単一リージョン」を前提にしている | 未記載の前提 | 未決の欄 (既に決めていたなら決定の欄に記録) |
| 構成図はキューを経由しているのに、本文は同期呼び出しと書いている | 本文と図表の不一致 | 欠陥候補の欄 |
| レート制限を追加してはどうか | 改善提案 | 提案の欄 (決定の欄には入れない) |

## 適用と判断

**向いている場面**
- 人がレビューする前に、書かれていない前提や本文と図表の食い違いを洗い出したいとき。
- 週2回までは追加料金なしで試せる。それを超えたら自分の Gemini API キーで上限を上げる。40ページの目安は約 $3.00〜$20 (製品 FAQ だけに書かれた目安)。

**判断の基準**
- 報告は3種に分けてから採否を決める。どの欄に書き戻すかは、指摘ごとに人が選ぶ。
- 精度を引用するときは「PAT・26 論文 29 誤り・Gemini 3.1 Pro・独自グレーダ・89.7%」の範囲に限る。
- この判断が変わる条件: 公開製品で、設計文書での検出率と偽陽性率が、著者以外の評価によって同じ母集団定義で示されたとき。そうなれば、設計レビューの精度として引用してよい。
- 未公開の仕様は、画面に出る保存条件の3つの文言を並べて確認してから出す。改善へのオプトインや1年保存を受け入れられないなら出さない。

## 限界・注意点

- 画像としてしか残らない図は、プレーンテキストや、画像が落ちた大きな PDF では照合できない。20MB (20×1024×1024 バイト) を超えるファイルはクライアントが受け付けない。
- 受け付ける入力形式の記述が、一次ソースごとに違う (ブログ / FAQ / ファイル選択画面の拡張子)。複数ファイルをまとめて投入する機能は、告知の時点では「今後対応」。
- 著者調査の数字は、論文と ICML ブログで母集団が違う (helpful は 90.7% と 73.3%)。
- 関連研究を探すために Web 検索をすることがある。Gemini API の deep-review ドキュメントは、2026-10-17 時点で 404 だった。

**公開資料ではまだ分からないこと**
- 追加料金なしの Medium が、会議での試行と同じ計算量か。
- 20MB 未満の PDF・PPTX・Google スライドで、画像としての図表が点検に使われるか。
- オプトインの初期値と、「Deep Review の改善」にモデルの学習が含まれるか。
- 外部検索のクエリに、未公開文書の文章が含まれるか。
- 公開製品での偽陽性率と、設計文書での独立した評価。
