# 連続不正アクセスの公開APIを台帳と認可で止める

元記事: [連続不正アクセスの公開APIを台帳と認可で止める](../../../../../articles/ai-api-blogs-jpcert-or-jp-p6_20261016.md)

## ひとことで言うと

インターネットから応答する面を台帳にまとめ、未修正か認可なしで応答している状態を止める。公表された送信元は、文書ごとのリストのまま自社ログと照合する。

## 核心ポイント

1. 台帳に行が無いと、レート制限・認可・トークン寿命・公開停止をどこに適用するか決まらない。従業員向けの管理系や BI も被害に遭っているので、同じ台帳に載せる。
2. 止める基準は侵入の成功ではなく、既知の穴・設定不備・認可なしの面が応答している時点に置く。注意喚起は、単一製品の脆弱性を共通原因とはしていない。
3. アプリ内の秘密・署名・難読化は、サーバの認可の代わりにならない。公開アプリは解析される前提で、オブジェクト単位の認可と、外部 URL を取得する API の宛先制限をサーバで行う。
4. 公表された送信元リストは文書ごとに別で、正規利用の可能性の注記も文書ごとに違う。リストを結合せず IP の完全一致で照合し、一致しても IP だけで侵害とは断定しない。
5. 観測された攻撃は、同じ送信元の中でツールと手順を段階的に変える。単発のシグネチャで調査を閉じず、その送信元の前後 8 時間を 1 本の時系列で見る。

## メンタルモデル

![公開面を止める5つの作業単位](images/structure.png)

台帳が、既知の穴を突き合わせる対象と、認証・認可・レート制限・宛先制限の適用先を決める。許可と拒否はアクセスログに残し、同じ送信元の手順の変化を 1 本の記録にまとめて台帳へ戻す。

![指標は文書に、対策は公開面に](images/structure-2.png)

侵害指標 (不審な送信元など) は、それを公表した文書に付けたまま持つ。公開面とつなぐのは攻撃類型と対策だけで、複数の文書の指標を 1 つの攻撃元リストにまとめない。

## 具体例

記事が台帳の形として置いた例示の行で、実在の組織の行ではない。

| 行 | 主な値 | 読み方 |
|---|---|---|
| 会員プロフィール API | 顧客向け、運用は委託先、認可はオブジェクト単位 | 委託先が運用していても、自社の台帳から外さない |
| 従業員向け BI | 従業員向け、インターネット公開、認可はネットワーク制限のみ | 注意喚起が点検を求めた組み合わせで、顧客向け API より先に見る |

## 適用と判断

向く場面:

- 自社か委託先が、アプリ・API・管理系・BI をインターネットに公開している
- 複数の公表元から届いた送信元リストを、自社ログと照合する
- 公開しているモバイルアプリのバックエンドを点検する

確認項目:

- 従業員・管理者向けでインターネットに公開している面を、顧客向け API より先に点検したか
- 本番のルート一覧と台帳の差を週次で確認し、増えたルートは認可とレート制限が付くまで公開を止めているか
- ログイン・パスワード再設定・SMS 送信を、閲覧 API と別のカウンタで制限し、拒否した回数も記録しているか
- 外部 URL を取得する API で、リダイレクトのたびに許可先を判定し直しているか
- ログが委託先の WAF にしか無い面を把握しているか

## 限界・注意点

- AI 利用の確度は資料で違う。JPCERT/CC は AI の利用を確認したと書くが判定手順とモデル名は示しておらず、NICT は効率化の可能性を書くにとどまる。
- ビットフォレストの AI エージェント判定は、自社 WAF の仕掛けに依存し、手法は非公開である。自社ログの判定には使えない。
- 注意喚起は、全事案が同じ手法だとは書いていない。ビットフォレストが観測した 3 つの送信元にはスマホアプリの User-Agent が無く、アプリ解析起点の攻撃 (NICT の言う A2B) の実例とは扱えない。
- 記事中のレート制限の値と調査開始の目安は例示で、注意喚起が指定した値ではない。
- 不明点: JPCERT/CC が公表した IP と調査した 3 台のサーバの対応、ビットフォレストの判定方法は公開されていない。
